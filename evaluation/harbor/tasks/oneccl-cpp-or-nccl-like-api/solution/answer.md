Keep the existing service on the oneCCL C++ API. It already owns `ccl::kvs`, communicator, stream, and event lifecycles through `oneapi/ccl.hpp`; rewriting proven C++ orchestration only because the C names resemble NCCL adds risk without satisfying the actual pure-C interoperability need. Treat the NCCL-like oneCCL C API as a separate, version-gated integration surface, not as source, binary, or behavioral compatibility with NVIDIA NCCL.

Put any supported C API behind a narrow C adapter at the plugin boundary. The adapter should expose only the collectives and lifecycle operations the plugin needs and should own one API's handles from initialization through destruction. Do not cast, mix, or share C and C++ communicator, stream, event, or KVS handles, and do not initialize two independent communication worlds accidentally. If the deployed release does not document and export the required C calls, either keep the plugin adapter in C++ with an `extern "C"` application-facing wrapper or upgrade the complete oneCCL package coherently; do not copy declarations or emulate missing ABI symbols.

Establish support from the production artifact, not from repository `main`. Record the exact oneCCL package/version and build configuration. Inventory `oneapi/ccl.hpp` and `oneapi/ccl.h`, then compile the release-matched official C++ and C examples against the production include directory. Inspect the loaded `libccl` with the link map, `ldd`, and `nm -D` or `readelf -Ws` for each required C symbol. Use documentation and examples published for that exact release, including deprecation or experimental status. Capture compiler, include and library paths, link flags, runtime loader paths, plugin/transport, launcher, and `CCL_*` environment consistently across ranks. A header's presence does not prove that every newer declaration or symbol is available.

Classify the current error before changing APIs. Missing declarations are a source/header-version mismatch; undefined references are a link target, library version, or unavailable-symbol problem. A loader failure is a runtime library-path/ABI problem. Only after the binary starts should rank mapping, KVS/communicator creation, plugin visibility, collective ordering, and buffer contracts be investigated. Log the selected API, library identity, global/local rank, communicator size, operation sequence, datatype, element count, reduction/root, in-place mode, plugin/transport, and completion state per rank.

For either API, every rank must build one compatible communicator and enter the same collective sequence with matching count, datatype, reduction, and buffers. Retain the returned event/request and wait, or establish an explicit dependency chain, before reading, reusing, or freeing destination storage. The adapter must document who owns initialization, communicators, buffers, requests, and finalization, and it must translate errors without hiding asynchronous failures.

Create two independent two-rank smoke programs. The C++ program should use the existing KVS/communicator/stream path and sum fixed vectors such as rank 0 `[1,2,3,4]` and rank 1 `[10,20,30,40]`; both ranks must receive `[11,22,33,44]` after explicit completion. Build the equivalent pure-C test only when the installed release's headers, symbols, and release documentation confirm the required API. Run both through the production launcher and plugin with rank-prefixed logs. Add a configure or compile-time feature test that rejects an older image missing the required C declarations/symbols instead of discovering it in production.

Roll out the adapter behind a feature flag with separate CI jobs for every supported oneCCL release. Keep the C++ implementation as the reference until C-path parity is demonstrated for initialization, failure propagation, and required collectives. Compare every rank against deterministic expected results, then test odd counts, in-place use, asynchronous completion, and process failure handling. Only after correctness should representative sizes, rank counts, topology, warmup, repeated iterations, and per-rank latency be benchmarked. Bound any API-performance claim to the tested release, plugin, transport, topology, and hardware.
