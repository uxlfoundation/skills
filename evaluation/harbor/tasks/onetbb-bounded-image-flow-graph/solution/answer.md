The failure is unbounded admission, not evidence that the machine needs more workers. An `unlimited` `function_node` with the default queueing behavior can accept or buffer messages faster than downstream stages retire them. Because every message owns a large image until write completes, queue depth becomes retained memory and RSS rises. Blocking decode I/O occupies scheduler workers, while the nested `parallel_for` and the framework's foreign thread pool add oversubscription and contention; more outer concurrency can therefore worsen tail latency.

Use a `oneapi::tbb::flow::graph` with an explicit admission bound. Put a `limiter_node<Image>` before the resource-owning stages, or use the documented rejecting-node/input-node backpressure pattern. Choose the threshold from a memory budget and a measured concurrency sweep, not the number of submitted files. Connect the terminal write/cleanup result to the limiter's `decrementer()` with a `continue_msg`. Every admitted token must be returned exactly once after the buffer is released, including decode, inference, write, cancellation, and exception paths; use an RAII completion object or an error edge so failures cannot leak capacity.

Give each `function_node` a deliberate limit. Decode should have a small limit appropriate for blocking I/O or be moved to a separate I/O facility that feeds the graph. Inference should use the library's measured useful parallelism. Avoid nesting an unconstrained `parallel_for` inside many concurrent inference bodies: either make the outer inference node's body serial/library-owned, cap the outer node so inner work can use the arena, or isolate a justified inner arena after measurement. Make write serial only if the sink or ordering contract requires it. Run the graph in a `task_arena` with a stated maximum, or coordinate a process-wide `global_control` limit with the existing framework pool so total runnable threads stay near the available cores.

First compare decoded/inferred/written values with the serial reference on fixed images, including corrupt input and injected stage failures. Carry an image ID through every message, define whether output order matters, and verify no duplicate, missing, or mis-associated result. Exercise cancellation and exceptions while counting admissions, completions, live buffers, and ownership releases.

For resource evidence, record in-flight count and each node's queue depth, live image bytes, peak and steady RSS, oneTBB and foreign-pool thread counts, CPU utilization, blocking time, and per-stage service time. A bounded design must reach a stable memory plateau under a long run.

After correctness and bounded lifetime pass, benchmark representative image sizes and a sustained stream. Warm up, repeat trials, and sweep the admission threshold, stage limits, arena limit, and framework-pool setting one variable at a time. Report throughput plus median and tail latency, peak RSS, CPU utilization, and stage bottlenecks. The supported claim is limited to the tested machine, graph limits, image mix, and framework configuration.
