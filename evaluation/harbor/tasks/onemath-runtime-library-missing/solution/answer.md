The successful `ONEMATH::onemath` link only confirms that the oneMath runtime-dispatch front end was found at link time. It does not prove that a domain-specific CUDA backend can be loaded or used at runtime.

Start with the failing domain and routine. For example, a BLAS GEMM on an NVIDIA device needs the corresponding cuBLAS-backed oneMath plugin; LAPACK, RNG, DFT, and sparse calls instead map to cuSOLVER, cuRAND, cuFFT, and cuSPARSE support. Inspect the oneMath build configuration, installation manifest, and installed shared libraries to verify that the required backend wrapper was enabled, built, and deployed. Do not infer one domain's availability from another.

Next, capture objective device and loader evidence. Print the selected SYCL queue's platform, device name, vendor, and backend, and retain output from `sycl-ls` and `nvidia-smi`. Run `ldd` on the application, oneMath runtime-dispatch library, and domain backend plugin. Use `LD_DEBUG=libs` for one failing run and inspect `LD_LIBRARY_PATH` plus each binary's RPATH/RUNPATH so the actual dynamic-linker search path and missing dependency are visible.

Check the oneMath support matrix and build notes for a supported configuration across the oneMath version, SYCL compiler, CUDA toolkit, NVIDIA driver, and relevant C++ ABI. A device being enumerated does not establish that this particular collection of versions is compatible.

Validate in stages. Use a minimal GEMM with small deterministic inputs, compute a known-answer result, and compare it with a CPU reference using an appropriate floating-point tolerance. Force synchronization with the returned event's `wait_and_throw()` (or the queue equivalent) so asynchronous errors are observed. Once correctness passes, exercise a representative problem size after warm-up and capture an `nsys` profiler trace. Confirm that CUDA kernels execute on the intended GPU; only then use timing and performance as evidence that the expected backend is active.
