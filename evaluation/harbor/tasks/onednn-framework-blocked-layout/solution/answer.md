The integration is violating the memory-layout contract. The logical NCHW tensor shape does not establish a contiguous NCHW physical layout, and `format_tag::any` allows the convolution primitive descriptor to choose an optimized blocked destination. The framework must not reinterpret those bytes using its preferred strides.

Record the engine and device, convolution shapes, groups, strides and padding, source/weight/destination data types, accumulation and post-op attributes, oneDNN version, build type, threading runtime, and framework layout metadata. Query the finalized convolution primitive descriptor and log the actual source, weights, bias, and destination memory descriptors, including dimensions, padded dimensions, format kind, strides, and inner blocks. Runtime errors, oneDNN verbose output, nearby tests, and current documentation should establish backend support rather than an assumption.

At the framework boundary, compare the actual destination descriptor with the descriptor required by the consumer. Insert an explicit oneDNN reorder when they differ. If adjacent oneDNN primitives accept the optimized descriptor, keep the blocked layout internal and move the reorder to the first incompatible consumer; count and time every reorder. Do the same compatibility check for source and weights instead of assuming their logical labels describe physical storage.

Separate layout repair from fusion. Build a deterministic small unfused reference for convolution, bias, and ReLU, then compare the fused post-op or graph path with stated absolute and relative tolerances. Include edge values around zero so ReLU behavior is observable, and verify the framework-visible tensor after any required destination reorder. Do not tune or add fusion until the unfused path has parity.

Once correctness passes, benchmark the old and repaired paths with representative production shapes, the same engine, build, thread settings, and warmup. Use an equivalent benchdnn case or the project's benchmark to distinguish primitive time from integration overhead. Report primitive execution, reorder count and time, and end-to-end latency separately. A supported claim is limited to the measured shapes and environment; an optimized internal layout is beneficial only when its saved compute exceeds its reorder cost.
