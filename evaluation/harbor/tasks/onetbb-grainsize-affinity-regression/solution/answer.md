The primary regression is oversplitting. The current `blocked_range` has grainsize 1 and `simple_partitioner`, which disables automatic chunking for an inexpensive, memory-heavy body. The table's millions of body calls and poor small/medium times support scheduling and dispatch overhead, not a need for more threads. The coarse grain in `simple-g65536` is the opposite failure: only 16 bodies, worse p95, and likely idle cores or load imbalance. Body cost and problem size change the crossover, so no single fixed grain is established.

The placement result is independent. The same `auto-g4096` binary slows from 86.1 to 155.4 ms when workers span NUMA nodes but pages remain first-touched on node 0. `affinity_partitioner` only slightly changes that split-NUMA result; it is a cache-affinity hint that can reuse an iteration-to-thread pattern, not OS thread pinning or a NUMA-memory policy. Its warm, repeated, cache-sized medium result is promising, while the cold replacement-buffer and very large cases show little benefit.

Start the code repair with the default `auto_partitioner` and remove `simple_partitioner` plus the grainsize-1 constraint. Keep a serial cutoff for inputs whose completed call is slower in parallel. If measurements justify a lower chunk bound, select it from a sweep of grainsizes and body costs rather than copying 256 or 4096 into every loop. Consider `affinity_partitioner` only for repeated loops over the same or similarly mapped cache-resident buffers; retain the same partitioner object across those repetitions with a lifetime owned by that non-concurrent loop or request context.

Repair deployment evidence separately. Record the effective process CPU set, oneTBB arena concurrency, socket/core topology, NUMA page placement, first-touch path, compiler flags, and oneTBB version. Prefer local first-touch and a deliberate CPU/NUMA policy. If the service requires it, test a `task_arena` with measured `max_concurrency` and NUMA constraints against external `taskset`/cpuset or `numactl` placement; do not assume an affinity partitioner constrains operating-system scheduling.

Before performance selection, compare every output with the serial stencil using deterministic inputs and an explicit floating-point tolerance, including boundaries and odd sizes. Then cross input sizes, low/high work per element, serial/auto/candidate grains and partitioners, thread counts, same/new buffers, and local/split placement. Change one factor at a time, warm up, run enough repetitions, and report median and p95 completed-call latency plus throughput.

Collect body/task counts, per-body duration, active workers, CPU utilization, context switches, migrations, cache misses, memory bandwidth, and remote-NUMA traffic. Keep a production choice only where correctness passes and the measured configuration improves the target sizes without unacceptable tails. Any claim must name the tested hardware, placement, thread count, oneTBB/build version, workload, reuse state, and timing boundary; no single measured setting is a universal choice.
