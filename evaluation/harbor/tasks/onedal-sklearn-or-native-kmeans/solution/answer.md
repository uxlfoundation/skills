Do not start with a C++ rewrite or assume a GPU path. For an existing scikit-learn pipeline, first test the Extension for Scikit-learn path because it preserves the Python estimator interface and minimizes integration and deployment change. Choose native oneDAL C++ only when the application needs direct C++ ownership, an explicit SYCL queue, table-level control, unsupported Python integration, or a measured bottleneck that the extension path cannot address.

Capture the sample and feature counts, dtype, dense or sparse representation, memory size, missing-value handling, scaling and other preprocessing, train/test boundaries, random seed, initialization method, cluster count, iteration limit, convergence tolerance, and required scikit-learn behavior. Record the target CPU or GPU, compiler and runtime, installed oneDAL and extension versions, and deployment boundary. Check current algorithm and device support instead of promising acceleration from device availability alone. Ordinary single-process input is a batch workload; online or distributed mode requires streaming or genuinely distributed data and a matching launcher.

Freeze a deterministic reference run before changing interfaces. Match preprocessing and KMeans parameters, then compare convergence status, iteration count, inertia or objective, and predictions. Cluster labels may be permuted, so align centers or labels before comparison and use stated numerical tolerances plus a task-level quality metric. Treat changed defaults, seeds, orientation, dtype, and row-major table construction as correctness hypotheses, not performance details.

Prototype the minimal-change extension path and, only if justified, a native oneDAL path that explicitly constructs the correct dense or sparse table and owns the queue. Verify data shape and row/column orientation at each boundary. Report unsupported or unverified feature and device combinations rather than silently falling back.

Benchmark representative dataset sizes after parity passes. Use the same inputs, initialization, stopping criteria, thread limits, device, and quality checks. Separate Python/import and setup time, table or array conversion, host-device transfer, training, prediction, synchronization, and teardown; also report end-to-end latency. Include warmup, multiple iterations, dispersion, hardware/software configuration, and peak memory. The supported claim should name the tested interface, data regime, device, conversion scope, and metric, rather than asserting that native C++ or GPU execution is always faster.
